# Архитектура OIMO v1

## Решение

Модульный монолит в одном процессе Node.js:

```
браузер ──► Next.js 16 (standalone server.js)
              ├─ app/*.tsx            интерфейс (клиентские компоненты)
              ├─ app/api/auth/[...all] Better Auth: регистрация, вход, сеансы, смена/сброс пароля
              ├─ app/api/oimo          бизнес-операции и выгрузка XLSX
              └─ app/api/photo         приём и выдача приватных фото
                     │
                     ▼
              lib/oimo/service.ts ──► lib/oimo/db.ts ──► SQLite (data/oimo.sqlite, WAL)
                                                 └──► data/photos/<workspace>/<uuid>
```

Доменная арифметика и календарь (`lib/oimo/domain.ts`) не зависят ни от базы, ни от способа входа. Одна база, одна папка данных и один процесс — достаточно для небольшой команды и просто для резервного копирования.

## Модули

- `lib/oimo/domain.ts` — календарь Бишкека, деньги в тыйынах, нормализация серийных номеров, чистая функция KPI, допустимые переходы статусов.
- `lib/auth.ts` — конфигурация Better Auth (email + пароль, сеансы, лимиты, опциональный SMTP). `lib/identity.ts` — получение сеанса на сервере. `lib/auth-client.ts` — клиент для форм.
- `lib/oimo/auth.ts` — членство и роль по стабильному `user.id`, проверка Origin, счётчики лимитов в таблице `limits`.
- `lib/oimo/service.ts` — бизнес-операции и проекции для владельца/продавца. Чтение данных продавцом ограничено на сервере.
- `lib/oimo/database.ts`, `lib/oimo/db.ts` — подключение SQLite (WAL, foreign keys, busy timeout) и небольшой адаптер `prepare/bind/batch`; `batch` выполняется одной транзакцией.
- `lib/oimo/xlsx.ts` — генерация OOXML с inline-строками (без формул).
- `migrations/*.sql` — версионированные миграции; `scripts/migrate.mjs` применяет каждую один раз в транзакции. `0003_better_auth.sql` содержит таблицы Better Auth (тот же DDL, что создаёт его программная миграция; `npm run setup` дополнительно сверяет схему после обновления Better Auth).
- `scripts/` — `setup.ts` (секрет + миграции), `start.mjs` (локальный production-запуск), `admin-reset-password.mjs`, `backup.mjs`, `docker-env.mjs`, `postbuild.mjs`.

## Аутентификация и сеансы

- Better Auth 1.7, только email + пароль. Пароль 12–128 символов, хеш scrypt.
- Сеанс 7 дней, хранится в БД (cookie-кеш выключен, поэтому выход и отзыв сеанса действуют сразу). Cookie `HttpOnly`, `SameSite=Lax`, `Secure` автоматически при `https://` в `BETTER_AUTH_URL`.
- Смена пароля завершает остальные сеансы; сброс пароля по письму завершает все.
- Старые заголовки платформы (`oai-authenticated-user-*`) ничего не дают: личность берётся только из сеанса (есть тест).
- Тело запросов к `/api/auth` ограничено 50 КБ.

### Разрешённые адреса (CSRF) и работа по Wi-Fi

`lib/origins.ts` — один список для Better Auth (`trustedOrigins` как функция) и для проверки `Origin` в API приложения. Входят только точные адреса: `BETTER_AUTH_URL`, `localhost`/`127.0.0.1`/`[::1]` на том же порту, `OIMO_TRUSTED_ORIGINS`, а при `OIMO_TRUST_LAN=true` (включается сам при `OIMO_HOST=0.0.0.0`) — собственные частные IPv4 этого компьютера и `<LocalHostName>.local` (на macOS имя берётся из `scutil`, потому что `os.hostname()` может вернуть IP). Список перечитывается раз в 30 секунд, поэтому смена IP по DHCP не требует перезапуска.

`OIMO_OPEN_TEST_ACCESS=true` — только для теста: принимается запрос, у которого `Origin` в точности равен `Host` запроса и этот хост локальный (loopback, частный IPv4, `169.254.x`, `*.local`, однословное имя). Сайты из интернета и DNS-rebinding-домены не проходят; вход и роли не меняются.

Клиентский код не использует API, доступные только в «безопасном контексте» (HTTPS или localhost): на `http://192.168.x.x` нет `crypto.randomUUID` и `navigator.clipboard`. `lib/browser.ts` даёт `uuid()` на `crypto.getRandomValues` и копирование с запасным вариантом; юнит-тест не даёт вернуть прямые вызовы.

### Лимиты против подбора и злоупотреблений

IP клиента ненадёжен: Next.js заполняет `X-Forwarded-For` адресом сокета, только если клиент не прислал заголовок сам. Поэтому:

| Уровень | Что ограничивает | Зависит от IP |
|---|---|---|
| `app/api/auth/[...all]/route.ts` | 10 неудачных входов на email за 15 мин; 30 регистраций в час на сервер; сброс пароля — 3 в час на email и 30 в час на сервер | Нет |
| Better Auth (таблица `rateLimit`) | вход 20/мин, регистрация 10/мин, сброс 5/мин, смена пароля 10/мин на IP | Да, best effort |
| `lib/oimo/auth.ts` | 120 бизнес-запросов в минуту на аккаунт, 15 загрузок фото в минуту и 300 МБ фото в сутки на сотрудника | Нет |

Подделка IP позволяет обойти только IP-уровень, но не лимиты по email/аккаунту и не общий лимит регистраций. Запрос с несколькими значениями `X-Forwarded-For` без `TRUSTED_PROXIES` попадает в общий для таких запросов bucket и не блокирует обычных пользователей. За обратным прокси задайте `TRUSTED_PROXIES` (IP/CIDR), тогда Better Auth берёт первый недоверенный адрес справа.

## Магазин, роли и приглашения

- Создание магазина — явное действие; создатель становится владельцем только этого магазина.
- Вошедший пользователь без магазина видит два пути: «Создать магазин OIMO» или «Открыть приглашение». Создание идемпотентно: если аккаунт уже владелец, повторный запрос возвращает успех; гонку двух запросов одного аккаунта разрешают уникальные индексы `workspaces.owner_id` и `members.user_id` (проигравший получает тот же магазин). Сотрудник другого магазина создать магазин не может (409).
- `OIMO_SINGLE_STORE=true`: только первый магазин на сервере; проверка повторяется внутри транзакции вставки (`INSERT … WHERE NOT EXISTS`), поэтому две одновременные «первые» регистрации не создадут два магазина (есть тест).
- Регистрация с email из приглашения сама по себе **ничего не даёт**. Доступ к чужому магазину — только через персональную ссылку и явное «Принять приглашение».
- Токен: 32 случайных байта, в базе только SHA-256, срок 7 дней, одноразовый, привязан к email участника. Новая ссылка аннулирует старую. Ссылка в части `#token=…` не уходит на сервер при открытии страницы и не попадает в логи.
- Привязка выполняется условным `UPDATE` в той же транзакции, что и погашение токена. Уникальный индекс `member_account` (`members.user_id`) гарантирует, что аккаунт состоит максимум в одном магазине даже при гонке «принять приглашение / создать магазин».
- С SMTP: перед принятием приглашения требуется подтверждённый email. Без SMTP email не проверяется — защита держится на секретности ссылки.
- Отключённый участник теряет доступ к API и фото на следующем запросе.

### Матрица доступа

| Действие | Владелец | Продавец |
|---|---|---|
| Создать продажу от своего имени | Да | Да |
| Подробные продажи и фото | Весь магазин | Только свои |
| Подтвердить, отклонить, вернуть | Да | Нет |
| Подробные начисления | Весь магазин | Только свои |
| Рейтинг | Имена и число ноутбуков | Имена и число ноутбуков |
| Каталог | Чтение и изменение | Чтение |
| Сотрудники, ссылки, правила, планы, корректировки, закрытие, выплаты | Да | Нет |
| XLSX и журнал действий | Да | Нет |

Проверка роли выполняется до разбора параметров, поэтому продавец получает 403, а не ошибку валидации.

## Продажа и согласованность

`pending → approved | rejected`, `approved → returned` (только в открытой неделе). Удаления нет. Повтор отправки с тем же UUID возвращает существующую запись.

Серийный номер: NFKC, верхний регистр, без пробелов. Частичный уникальный индекс `(workspace_id, serial)` для `pending/approved` отклоняет дубль на уровне БД. Фото проверяется по магазину и загрузившему сотруднику и не может быть прикреплено к двум активным продажам.

Переходы статуса используют версию строки и operation ID: `UPDATE ... WHERE version=?`, запись аудита вставляется только если `UPDATE` реально применился. Каждая денежная мутация повышает `workspaces.revision`. Закрытие недели сохраняет снимок (правило, строки начислений, ID/версии продаж) только если revision не изменился и нет продаж на проверке. Поздние изменения закрытой недели блокируются условием `NOT EXISTS (periods ...)` внутри самих вставок/обновлений.

## Рейтинги

Сервер считает рейтинг за сегодня, выбранную неделю, текущий месяц и год: только имя и число подтверждённых ноутбуков. Эти данные доступны всем участникам магазина; суммы начислений коллег продавцу не отдаются.

## Интерфейс

Один клиентский компонент `app/workspace.tsx`. От 761 px — боковое меню; до 760 px — тёмная шапка с логотипом, нижняя панель с центральной кнопкой «Продажа» и листом «Ещё» (набор пунктов зависит от роли, права всё равно проверяет сервер), модальные окна открываются снизу, таблица продаж становится карточками. Палитра — чёрный, белый, жёлтый из логотипа; шрифт не меньше 11 px; видимый фокус; зоны нажатия от 44 px.

## Деньги, планы, выплаты

Суммы — целые тыйыны; ставка переводится в тыйыны до умножения. Начальная формула не утверждена; утверждение — отдельная операция в журнале. Новые правила действуют с начала выбранной недели и не могут переписать неделю, где уже есть подтверждённые продажи. Планы на неделю/месяц/год независимы: штуки считают ноутбуки, выручка — все подтверждённые товары. Выплата — отметка уже сделанного платежа, уникальная на сотрудника и неделю.

## Фото

JPEG/PNG/WebP до 6 МБ, тип определяется по сигнатуре, имя — UUID сервера. Файлы лежат в `data/photos/<workspace>/` с правами 0600 и **не** раздаются статикой: только через `/api/photo` после проверки сеанса, магазина и роли, с `nosniff`, `Cache-Control: private, no-store` и `Content-Security-Policy: default-src 'none'; sandbox`. Это проверка формата, а не антивирус.

## Запуск и упаковка

- `next build --webpack` → `.next/standalone`; `scripts/postbuild.mjs` копирует `public/` и `.next/static` и удаляет из сборки любые `.env*`.
- Standalone-сервер делает `chdir` в свою папку, поэтому `scripts/start.mjs` переводит `OIMO_DATA_DIR` в абсолютный путь до запуска.
- Docker: многоэтапная сборка на `node:24-bookworm-slim`; в рантайм-образ попадают только standalone-сервер, `migrations/` и три скрипта. Пользователь `node`, том `/data`, миграции при старте, healthcheck на `/api/auth-config`. Секрет передаётся во время выполнения из `.env.docker`; при сборке используется заглушка, которая в образ не записывается.
- Заголовки безопасности для всех ответов: Content-Security-Policy (скрипты и запросы только к своему адресу, картинки self/blob/data, шрифты Google, `frame-ancestors 'none'`, `object-src 'none'`), `nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Permissions-Policy`. `script-src` содержит `'unsafe-inline'`, потому что Next встраивает загрузочные скрипты; nonce-CSP — возможное улучшение. HSTS должен ставить HTTPS-прокси.

## Развитие без переписывания

1. **До реальных выплат:** утвердить формулу и правила возвратов, пройти одну неделю параллельно с контрольной ведомостью, настроить ежедневные копии и проверить восстановление, включить HTTPS.
2. **Надёжность:** серверная пагинация и агрегаты, мониторинг ошибок, очистка неиспользованных фото (сейчас загруженные, но не прикреплённые фото остаются на диске), расширенный аудит «было/стало».
3. **Возвраты после закрытия:** отдельный return case с проверкой владельцем и корректировкой следующего периода, без изменения снимка.
4. **Склад:** физические экземпляры, закупки, перемещения, себестоимость; продажи ссылаются на экземпляр.
5. **Рассрочка:** программа финансирования, ожидаемые и полученные платежи.
6. **Масштаб:** PostgreSQL (заменить `lib/oimo/database.ts`/`db.ts`, перенести SQL; Better Auth поддерживает PostgreSQL), S3-совместимое хранилище для фото, несколько экземпляров за прокси (общая БД уже хранит сеансы и лимиты), выбор магазина для аккаунтов с несколькими членствами.
